## 4. Security — live-DB probes & remediation

### Confirmed live vulnerabilities (before fix)

| # | Finding | Probe result |
| --- | --- | --- |
| 1 | `user_profiles` anon SELECT exposes email/full_name/avatar (PII) | **LEAK: 3 rows returned to anon** |
| 2 | `mnemonic_generation_queue` world-writable by anon | **INSERT succeeded via anon key** |
| 3 | `mnemonics` INSERT/DELETE by any authenticated user (cache poisoning) | **DELETE allowed** |
| 4 | `/api/tts` POST unauthenticated (paid MiniMax/Edge synthesis, 10/min/IP) | confirmed (code) |

Items 1–2 were drafted in `20260816_security_hardening.sql` (08-16 audit) but **never applied** — the CLI migration history is drifted (remote uses short names; local long names never pushed), so `supabase db push` is blocked. Applied via Dashboard SQL Editor (user-run), file: `supabase/migrations/20260824_security_hardening.sql` (20260816 content + mnemonics restriction).

### Verified live after remediation (anon-key probes)

| # | Probe | Before | After |
| --- | --- | --- | --- |
| 1 | `user_profiles` anon SELECT | LEAK (3 rows) | BLOCKED (0 rows) |
| 2 | `mnemonic_generation_queue` anon INSERT | WRITABLE | BLOCKED (RLS violation) |
| 3 | `mnemonics` anon INSERT | WRITABLE | BLOCKED |

Root cause for #3 was **drifted dashboard-created policies** (`Anyone can insert/delete mnemonics` on `{public}`) plus RLS disabled on the table — none of the migrations knew about them. Final live policy state: view = public SELECT; write = `service_role` only. (Project runs PostgreSQL 14 — `FORCE ROW LEVEL SECURITY` unsupported; `ENABLE` suffices for PostgREST roles.)
